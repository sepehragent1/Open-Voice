## 📖 معرفی پروژه

**Open Voice (اوپن ویس)** یک برنامهٔ گفت‌وگوی صوتی با معماری **Peer-to-Peer (P2P)** است که با استفاده از Flutter و WebRTC توسعه داده شده و از برنامه‌هایی مانند Discord الهام گرفته است.

هدف این پروژه فراهم کردن راهی ساده برای برقراری ارتباط صوتی میان کاربران، بدون وابستگی به یک سرور مرکزی دائمی برای مدیریت تمام ارتباطات است.

در معماری Open Voice، رایانهٔ میزبان نقش **Signaling Server** را بر عهده دارد و کاربران برای ایجاد ارتباط با یکدیگر از WebRTC استفاده می‌کنند. در صورت برقرار شدن مسیر مستقیم، جریان صوتی مستقیماً میان دستگاه‌های کاربران منتقل می‌شود. برای برخی شبکه‌ها نیز ممکن است استفاده از سرور TURN ضروری باشد.

### ✨ ویژگی‌های اصلی

- 🎙️ گفت‌وگوی صوتی با استفاده از WebRTC
- 🔗 ارتباط Peer-to-Peer در صورت امکان
- 🖥️ امکان ایجاد اتاق با استفاده از نسخهٔ ویندوز
- 📱 پشتیبانی از نسخهٔ اندروید
- 🏠 خودمیزبان (Self-hosted)؛ بدون نیاز به یک سرور مرکزی دائمی برای مدیریت اتاق‌ها
- 🔐 استفاده از فناوری‌های امنیتی برای محافظت از ارتباط صوتی و رمزهای عبور
- 🪶 طراحی سبک با استفاده از Flutter
- 🌐 امکان استفاده از شبکهٔ اینترنت برای اتصال کاربران از مکان‌های مختلف

> **توجه:** معماری P2P به این معنی نیست که برنامه در تمام شرایط بدون هیچ سروری کار می‌کند. برای برقراری ارتباط اولیه به Signaling نیاز است و در برخی شرایط شبکه‌ای، TURN می‌تواند برای انتقال رسانه ضروری باشد.

## ⚠️ پیش‌نیازهای حیاتی

قبل از نصب و راه‌اندازی اتاق، موارد زیر را با دقت مطالعه کنید. بدون فراهم بودن شرایط لازم، اتصال کاربران ممکن است برقرار نشود.

### ۱. میزبان باید از نسخهٔ ویندوز استفاده کند

شخصی که اتاق را ایجاد می‌کند، یعنی **Host**، باید نسخهٔ ویندوزی Open Voice را اجرا کند.

نسخهٔ ویندوز نقش **Signaling Server** محلی را بر عهده دارد. این سرویس اطلاعات مورد نیاز برای شروع ارتباط میان کاربران را تبادل می‌کند.

بنابراین، برای ایجاد اتاق نمی‌توان صرفاً از نسخهٔ اندروید استفاده کرد.

### ۲. دسترسی به پنل مدیریت مودم یا روتر

میزبان باید به پنل مدیریت Router خود دسترسی داشته باشد تا بتواند تنظیمات **Port Forwarding** را انجام دهد.

اگر Port Forwarding به‌درستی تنظیم نشده باشد، کاربران خارج از شبکهٔ میزبان ممکن است نتوانند به Signaling Server متصل شوند.

### ۳. بررسی Public IP و وضعیت CGNAT

برای اتصال کاربران از اینترنت، میزبان باید وضعیت آدرس IP عمومی و شبکهٔ خود را بررسی کند.

داشتن آدرس IPv4 عمومیِ قابل دسترسی از اینترنت، برای روش معمول Port Forwarding اهمیت دارد. اگر اینترنت میزبان پشت CGNAT باشد، تنظیم Port Forwarding روی روتر به‌تنهایی معمولاً کافی نیست.

در چنین شرایطی، بسته به معماری و تنظیمات برنامه، ممکن است به راهکار دیگری مانند دریافت IPv4 عمومی از ارائه‌دهندهٔ اینترنت یا استفاده از یک سرور TURN نیاز داشته باشید.

### ۴. سرور TURN برای شبکه‌های موبایل

استفاده از TURN برای کاربرانی که از اینترنت موبایل استفاده می‌کنند، به‌ویژه در شبکه‌های دارای CGNAT، **به‌شدت توصیه می‌شود**.

TURN می‌تواند در شرایطی که ارتباط مستقیم WebRTC برقرار نمی‌شود، رسانه را از طریق یک سرور واسط انتقال دهد.

> **نکته:** سرور TURN جایگزین خودکار Signaling Server نیست. این دو سرویس وظایف متفاوتی دارند.

## 📥 راهنمای نصب

### 🖥️ نصب نسخهٔ ویندوز

نسخهٔ ویندوز برای میزبانی اتاق ضروری است. بسته به فایل‌هایی که در بخش Releases مخزن منتشر شده‌اند، یکی از روش‌های زیر را انتخاب کنید.

**روش اول: فایل Setup.exe**

1. وارد صفحهٔ [Releases پروژه](https://github.com/sepehragent1/Open-Voice/releases) شوید.
2. آخرین نسخهٔ منتشرشده را باز کنید.
3. فایل نصب ویندوز با پسوند `.exe` را دریافت کنید.
4. فایل Setup را اجرا کنید و مراحل نصب را انجام دهید.
5. پس از نصب، Open Voice را اجرا کنید.

**روش دوم: نسخهٔ Portable**

1. فایل ZIP مربوط به نسخهٔ Portable را از بخش Releases دریافت کنید.
2. فایل را در یک پوشه استخراج کنید.
3. فایل اجرایی برنامه را از داخل پوشه اجرا کنید.

نسخهٔ Portable معمولاً به نصب جداگانه نیاز ندارد؛ با این حال، محتویات بسته باید به‌طور کامل استخراج شوند.

اگر فایل را از مخزن رسمی پروژه دریافت کرده‌اید و از سالم بودن آن اطمینان دارید، در صورت نمایش هشدار زیر:

## 🏠 راه‌اندازی اتاق صوتی

این بخش برای شخصی است که می‌خواهد اتاق را ایجاد کند و سایر کاربران را به آن متصل کند.

### مرحلهٔ اول: اجرای برنامه در ویندوز

Open Voice را روی رایانهٔ ویندوزی اجرا کنید.

رایانهٔ میزبان باید هنگام استفاده از اتاق روشن بماند و برنامهٔ میزبان در حال اجرا باشد. خاموش شدن رایانه یا متوقف شدن سرویس Signaling می‌تواند مانع اتصال کاربران جدید شود و بسته به پیاده‌سازی برنامه، ارتباط‌های موجود را نیز مختل کند.

### مرحلهٔ دوم: تنظیم پورت

در تنظیمات مربوط به میزبانی یا Signaling، پورت را روی مقدار زیر قرار دهید:

`8080`

این پورت باید در تنظیمات برنامه، Windows Firewall و Router با یکدیگر سازگار باشد.

### مرحلهٔ سوم: پیدا کردن آدرس IP داخلی رایانه

در ویندوز، Command Prompt را باز کنید و دستور زیر را اجرا کنید:

```cmd
ipconfig
```

در خروجی، آدرس IPv4 مربوط به آداپتور شبکه‌ای را پیدا کنید که رایانه از طریق آن به روتر متصل است.

برای مثال:

```text
IPv4 Address . . . . . . . . . . : 192.168.1.100
```

در این مثال، `192.168.1.100` آدرس داخلی رایانه است. آدرس واقعی شما ممکن است متفاوت باشد.

بهتر است در تنظیمات Router یک DHCP Reservation برای رایانهٔ میزبان ایجاد کنید تا آدرس داخلی آن تغییر نکند.

### مرحلهٔ چهارم: پیدا کردن Public IP

برای مشاهدهٔ IP عمومی، می‌توانید از یک سرویس معتبر نمایش IP استفاده کنید؛ برای مثال:

[https://ifconfig.me](https://ifconfig.me)

اگر IPv4 عمومی قابل استفاده باشد، آدرس نمایش‌داده‌شده معمولاً همان آدرسی است که کاربران بیرون از شبکه باید برای دسترسی به میزبان استفاده کنند.

با این حال، اگر شبکه پشت CGNAT باشد یا روتر دیگری در مسیر وجود داشته باشد، ممکن است Port Forwarding معمولی کار نکند.

### مرحلهٔ پنجم: اشتراک‌گذاری اطلاعات اتصال

پس از انجام تنظیمات شبکه، اطلاعات لازم برای اتصال را در اختیار کاربران قرار دهید.

این اطلاعات باید با روش اتصال و فیلدهایی که نسخهٔ فعلی برنامه ارائه می‌دهد مطابقت داشته باشند. برای مثال، اگر برنامه از آدرس سرور و پورت استفاده می‌کند، کاربران باید آدرس عمومی قابل دسترسی میزبان و پورت صحیح را وارد کنند.

**نکتهٔ امنیتی:** اطلاعات ورود، رمزهای عبور و سایر داده‌های محرمانه را در مخزن عمومی GitHub یا در پیام‌های عمومی منتشر نکنید.

## 🌐 تنظیمات شبکه و Port Forwarding

برای دسترسی کاربران از اینترنت، باید ترافیک مورد نیاز به رایانهٔ میزبان هدایت شود.

در این راهنما فرض می‌کنیم پورت Signaling برابر با `8080` است.

### ۱. تنظیم Windows Firewall

Windows Firewall ممکن است از دریافت اتصال‌های ورودی جلوگیری کند. برای مجاز کردن TCP و UDP روی پورت 8080، Command Prompt را با دسترسی Administrator اجرا کنید.

سپس دستورات زیر را وارد کنید:

**اجازهٔ اتصال TCP**

```cmd
netsh advfirewall firewall add rule name="Open Voice TCP 8080" dir=in action=allow protocol=TCP localport=8080
```

**اجازهٔ اتصال UDP**

```cmd
netsh advfirewall firewall add rule name="Open Voice UDP 8080" dir=in action=allow protocol=UDP localport=8080
```

این دستورات برای ایجاد Ruleهای ورودی هستند و به‌تنهایی تضمین نمی‌کنند که سرویس روی هر دو پروتکل در حال گوش دادن باشد.

اگر Signaling Server فقط از TCP استفاده می‌کند، Rule مربوط به UDP به‌تنهایی کاربردی برای آن سرویس نخواهد داشت. همچنین اگر برنامه برای ارتباط WebRTC از پورت‌ها یا پروتکل‌های دیگری استفاده می‌کند، باید قوانین متناسب با همان پیاده‌سازی را تنظیم کنید.

برای حذف قوانین بالا در آینده:

```cmd
netsh advfirewall firewall delete rule name="Open Voice TCP 8080"
netsh advfirewall firewall delete rule name="Open Voice UDP 8080"
```

> **توصیهٔ امنیتی:** به‌جای غیرفعال کردن کامل Windows Firewall، فقط قوانین لازم برای سرویس مورد نظر را ایجاد کنید.

### ۲. تنظیم Port Forwarding در Router

وارد پنل مدیریت روتر شوید. آدرس ورود به پنل بسته به مدل دستگاه متفاوت است و معمولاً در اطلاعات روتر یا بخش Default Gateway دستور `ipconfig` قابل مشاهده است.

در پنل، بخشی با یکی از نام‌های زیر پیدا کنید:

- Port Forwarding
- Virtual Server
- NAT
- Port Mapping

سپس یک قانون جدید بسازید.

| تنظیم | مقدار |
|---|---|
| Service Name | Open Voice |
| External Port | `8080` |
| Internal Port | `8080` |
| Internal IP | آدرس IPv4 داخلی رایانهٔ میزبان |
| Protocol | TCP و UDP، در صورت نیاز برنامه |
| Status | Enabled |

برای مثال، اگر آدرس داخلی رایانه `192.168.1.100` باشد، ترافیک ورودی پورت 8080 به همین آدرس و پورت داخلی 8080 هدایت می‌شود.

اگر Router امکان انتخاب هم‌زمان TCP/UDP را ندارد، دو قانون جداگانه بسازید.

پس از ذخیرهٔ تنظیمات، مطمئن شوید آدرس داخلی میزبان تغییر نکرده است.

### ۳. بررسی صحت تنظیمات

برای بررسی اینکه سرویس TCP واقعاً روی پورت 8080 گوش می‌دهد، در PowerShell اجرا کنید:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 8080
```

اگر هیچ نتیجه‌ای نمایش داده نشد، ممکن است سرویس اجرا نشده باشد یا از پورت دیگری استفاده کند.

می‌توانید از یک دستگاه خارج از شبکهٔ میزبان نیز اتصال را آزمایش کنید. آزمایش از داخل همان شبکه همیشه معیار مناسبی نیست، زیرا برخی روترها از NAT Loopback پشتیبانی نمی‌کنند.

**مهم:** باز بودن پورت در Firewall یا وجود Rule در Router به‌تنهایی اثبات نمی‌کند که اتصال از اینترنت برقرار خواهد شد. سرویس باید فعال باشد، مسیر شبکه درست تنظیم شده باشد و محدودیت CGNAT نیز وجود نداشته باشد.

## 🔄 راه‌اندازی سرور TURN

### TURN چیست و چرا به آن نیاز داریم؟

WebRTC ابتدا تلاش می‌کند یک مسیر مناسب برای ارتباط میان دو دستگاه پیدا کند. در بسیاری از شبکه‌ها، ارتباط مستقیم P2P برقرار می‌شود؛ اما در برخی شبکه‌ها، به‌خصوص شبکه‌های موبایل، NAT و CGNAT ممکن است مانع ایجاد مسیر مستقیم شوند.

در این شرایط، **TURN** می‌تواند ترافیک رسانه را از طریق یک سرور واسط انتقال دهد.

برای مثال، ممکن است میزبان با اینترنت خانگی در دسترس باشد، اما یکی از کاربران با اینترنت موبایل نتواند مسیر مستقیم مناسبی ایجاد کند. اگر برنامه و تنظیمات شبکه اجازه دهند، TURN می‌تواند مشکل مسیر رسانه را برطرف کند.

### مرحلهٔ اول: آماده‌سازی سرور

به یک سیستم Ubuntu یا محیط WSL با دسترسی لازم برای نصب و اجرای Coturn نیاز دارید.

برای نصب Coturn در Ubuntu:

```bash
sudo apt update
sudo apt install coturn
```

در محیط WSL، دسترسی شبکه، آدرس IP، فایروال و نحوهٔ دسترسی از اینترنت را جداگانه بررسی کنید. نصب Coturn در WSL به‌تنهایی باعث نمی‌شود سرور از اینترنت قابل دسترسی باشد.

برای استفادهٔ پایدار، معمولاً یک سرور دارای آدرس IP عمومی و تنظیمات شبکهٔ مناسب انتخاب بهتری است.

### مرحلهٔ دوم: اجرای Coturn

دستور زیر نمونهٔ اجرای Coturn با تنظیمات مشخص‌شده برای این راهنما است:

```bash
sudo turnserver -n -a -u myuser:mypassword -r myrealm -p 5349 -L 0.0.0.0 --min-port 49152 --max-port 65535
```

معنی پارامترهای مهم:

| پارامتر | توضیح |
|---|---|
| `-n` | اجرا بدون خواندن فایل پیکربندی |
| `-a` | فعال‌سازی احراز هویت |
| `-u` | تعیین نام کاربری و رمز عبور |
| `-r` | تعیین Realm مربوط به احراز هویت |
| `-p 5349` | تعیین پورت شنوندهٔ TURN |
| `-L 0.0.0.0` | گوش دادن روی تمام آدرس‌های محلی IPv4 |
| `--min-port` | حداقل پورت محدودهٔ Relay |
| `--max-port` | حداکثر پورت محدودهٔ Relay |

در این مثال، `myuser`، `mypassword` و `myrealm` مقادیر نمونه هستند. آن‌ها را با اطلاعات واقعی و مناسب محیط خود جایگزین کنید.

برای استفادهٔ عمومی، رمز قوی انتخاب کنید و از قراردادن اطلاعات محرمانه در مخزن عمومی خودداری کنید.

### مرحلهٔ سوم: باز کردن پورت‌های TURN

پورت `5349` پورت شنوندهٔ TURN در این پیکربندی است؛ پورت‌های `49152` تا `65535` نیز محدودهٔ پورت‌های Relay هستند.

برای دسترسی از اینترنت، بسته به پروتکل‌های مورد استفاده و تنظیمات سرور، باید پورت شنونده و محدودهٔ Relay در فایروال سرور و در صورت وجود NAT، در روتر یا لایهٔ شبکهٔ مربوطه مجاز باشند.

در پیکربندی نمونه، پورت شنونده روی 5349 تنظیم شده است. این عدد به‌تنهایی به معنای فعال بودن TURN over TLS نیست؛ برای استفاده از TLS باید گواهی، تنظیمات مربوطه و آدرس مناسب سرور را نیز پیکربندی کنید.

برای دسترسی قابل اعتماد از اینترنت، همچنین باید موارد زیر بررسی شوند:

- آدرس عمومی سرور و تنظیمات NAT
- قوانین Firewall و Security Group
- دسترسی به محدودهٔ پورت‌های Relay
- تنظیمات آدرس خارجی Coturn در شبکه‌های دارای NAT
- پشتیبانی کلاینت از روش و پروتکل انتخاب‌شده

### مرحلهٔ چهارم: وارد کردن اطلاعات در Open Voice

در بخش **TURN Config** برنامه، مقادیر زیر را وارد کنید. نام دقیق فیلدها ممکن است با نسخهٔ برنامه متفاوت باشد.

| فیلد | مقدار نمونه |
|---|---|
| TURN Server / Host | آدرس IP عمومی یا دامنهٔ سرور |
| Port | `5349` |
| Username | `myuser` |
| Password | رمز انتخاب‌شده برای TURN |
| Realm | `myrealm`، در صورتی که برنامه این فیلد را ارائه می‌دهد |
| Transport | پروتکل پشتیبانی‌شده توسط برنامه و سرور |

اگر برنامه آدرس کامل URI را می‌پذیرد، قالب آدرس معمول TURN می‌تواند به شکل زیر باشد:

```text
turn:YOUR_SERVER_IP:5349?transport=udp
```

این نمونه برای انتقال TURN روی UDP است. پروتکل، URI و فیلدهای مورد استفاده باید با قابلیت‌های پیاده‌سازی WebRTC در نسخهٔ فعلی برنامه هماهنگ باشند.

**نکتهٔ مهم:** ورود اطلاعات TURN به برنامه بدون فعال بودن سرور، باز بودن پورت‌ها و سازگاری پروتکل‌ها کافی نیست. برای آزمایش، ابتدا دسترسی به خود سرور و سپس برقراری ارتباط صوتی را بررسی کنید.

## 🔐 امنیت

امنیت ارتباطات یکی از جنبه‌های مهم برنامه‌های گفت‌وگوی صوتی است. Open Voice از فناوری‌های زیر استفاده می‌کند.

### ۱. DTLS-SRTP و امنیت صوت

WebRTC از سازوکارهایی مانند DTLS و SRTP برای محافظت از ارتباط رسانه‌ای استفاده می‌کند.

- **DTLS:** برای برقراری ارتباط امن و مذاکرهٔ کلیدها در شرایط مربوط به WebRTC استفاده می‌شود.
- **SRTP:** برای محافظت از جریان رسانه، از جمله داده‌های صوتی، در مسیر انتقال به کار می‌رود.

این فناوری‌ها به محافظت از جریان صوتی در مسیر انتقال کمک می‌کنند. با این حال، امنیت نهایی به پیاده‌سازی صحیح، مذاکرهٔ امن کلیدها، اعتبارسنجی اتصال و تنظیمات برنامه وابسته است.

### ۲. Argon2id و محافظت از رمزهای عبور

**Argon2id** یک الگوریتم هش رمز عبور است که برای افزایش هزینهٔ محاسباتی حملات حدس رمز طراحی شده است.

استفاده از Argon2id در سیستم مدیریت رمز عبور می‌تواند به محافظت از اطلاعات احراز هویت کمک کند. هش رمز عبور با رمزنگاری قابل بازگشت تفاوت دارد؛ در یک پیاده‌سازی مناسب، رمز اصلی برای مقایسهٔ اعتبار رمز ورودی مستقیماً ذخیره نمی‌شود.

### ۳. ملاحظات امنیتی برای میزبان

- فقط پورت‌های مورد نیاز را در Firewall باز کنید.
- برای حساب‌ها و سرویس TURN از رمزهای قوی استفاده کنید.
- از انتشار رمزهای عبور و اطلاعات محرمانه در مخزن عمومی خودداری کنید.
- نرم‌افزار و وابستگی‌ها را از منابع معتبر دریافت کنید.
- سرورهای عمومی TURN را بدون احراز هویت و محدودیت مناسب در معرض اینترنت قرار ندهید.
- در صورت استفاده از سرور عمومی، محدودیت مصرف و دسترسی را در نظر بگیرید.

> **توجه:** رمزنگاری رسانه به‌تنهایی به معنی ناشناس بودن کامل کاربران، پنهان ماندن IP آن‌ها یا امن بودن تمام اجزای سیستم نیست. ارتباطات P2P و تنظیمات شبکه ممکن است اطلاعاتی مانند آدرس IP را میان طرف‌های ارتباط آشکار کنند.

## 🧰 عیب‌یابی

### مشکل ۱: کاربران نمی‌توانند به اتاق متصل شوند

موارد زیر را بررسی کنید:

1. برنامهٔ ویندوز روی رایانهٔ میزبان اجرا شده باشد.
2. پورت تنظیم‌شده در برنامه با پورت Firewall و Router مطابقت داشته باشد.
3. آدرس داخلی رایانهٔ میزبان تغییر نکرده باشد.
4. قوانین Port Forwarding به آدرس صحیح اشاره کنند.
5. اتصال اینترنت میزبان فعال باشد.
6. شبکهٔ میزبان پشت CGNAT نباشد، یا راهکار مناسب برای آن در نظر گرفته شده باشد.

### مشکل ۲: اتصال برقرار می‌شود اما صدایی شنیده نمی‌شود

برقراری Signaling لزوماً به معنای موفق بودن مسیر رسانه نیست.

موارد زیر را بررسی کنید:

- مجوز دسترسی به میکروفون در ویندوز و اندروید
- انتخاب ورودی و خروجی صوتی صحیح
- وضعیت قطع یا وصل بودن میکروفون
- تنظیمات WebRTC و مذاکرهٔ رسانه
- وجود خطا در ICE Candidateها
- دسترسی به سرور TURN، در صورت استفاده
- باز بودن پورت‌های Relay و سازگاری تنظیمات TURN

اگر کاربران از اینترنت موبایل یا شبکه‌های محدودشده استفاده می‌کنند، یک TURN Server با تنظیمات صحیح می‌تواند مشکل مسیر رسانه را برطرف کند.

### مشکل ۳: کاربران با اینترنت موبایل متصل نمی‌شوند

برخی اپراتورها از CGNAT استفاده می‌کنند و امکان ایجاد ارتباط مستقیم بین دستگاه‌ها را محدود می‌کنند.

در این شرایط:

1. اتصال با یک شبکهٔ دیگر را آزمایش کنید.
2. مطمئن شوید TURN Server از اینترنت قابل دسترسی است.
3. اطلاعات TURN را دقیق وارد کنید.
4. پورت شنونده و محدودهٔ Relay را بررسی کنید.
5. گزارش‌های Coturn و WebRTC را برای یافتن خطا بررسی کنید.

اگر TURN درست پیکربندی نشده باشد، صرفاً فعال کردن گزینهٔ TURN در برنامه مشکل را حل نمی‌کند.

### مشکل ۴: اتصال پس از مدتی قطع می‌شود

قطع شدن ارتباط می‌تواند دلایل مختلفی داشته باشد:

- بسته شدن برنامهٔ میزبان
- خاموش شدن یا قطع اینترنت رایانهٔ میزبان
- تغییر شبکه یا IP
- منقضی شدن یا تغییر مسیر ارتباطی WebRTC
- محدودیت‌های NAT یا Firewall
- ناپایداری اینترنت یکی از کاربران
- متوقف شدن سرور TURN

ابتدا مشخص کنید که آیا Signaling Server همچنان فعال است و آیا ارتباط رسانه نیز از بین رفته است. بررسی گزارش‌های برنامه و سرور به تشخیص دقیق‌تر کمک می‌کند.

### مشکل ۵: اتصال از داخل شبکه کار می‌کند، اما از اینترنت نه

این وضعیت معمولاً نشان می‌دهد که مشکل به مسیر دسترسی خارجی مربوط است.

موارد مهم عبارت‌اند از:

- Port Forwarding نادرست
- آدرس داخلی اشتباه
- CGNAT
- وجود روتر دوم یا Double NAT
- قوانین Firewall
- پشتیبانی نکردن Router از NAT Loopback هنگام آزمایش با Public IP از داخل شبکه

برای آزمایش واقعی دسترسی خارجی، از یک دستگاه روی شبکه‌ای متفاوت استفاده کنید.

### مشکل ۶: دستور Flutter اجرا نمی‌شود

اگر دستورهای Flutter خطا می‌دهند:

```bash
flutter doctor
flutter pub get
```

خروجی آن‌ها را بررسی کنید. معمولاً خطاهای مربوط به SDK، وابستگی‌ها، مجوزها یا ابزارهای کامپایل در همین مرحله مشخص می‌شوند.

### مشکل ۷: سرور TURN اجرا می‌شود اما ارتباط برقرار نمی‌شود

موارد زیر را بررسی کنید:

- نام کاربری، رمز عبور و Realm
- آدرس عمومی سرور
- پورت شنوندهٔ TURN
- قوانین Firewall و NAT
- محدودهٔ پورت‌های Relay
- سازگاری پروتکل مورد استفادهٔ کلاینت و سرور
- تنظیمات TLS، در صورتی که از آن استفاده می‌کنید

همچنین توجه کنید که موفق بودن اتصال به پورت شنونده لزوماً به معنای قابل استفاده بودن پورت‌های Relay نیست.
